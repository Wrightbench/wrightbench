# Handoff: Wrightbench — Playwright Desktop App

## Overview
Wrightbench is a desktop studio for recording, running, debugging and reviewing Playwright test suites. The Electron app brings Playwright's CLI runs, UI Mode, codegen, trace viewer and HTML reports into one workspace, with multi-project management, persistent run history and flakiness analytics. The workspace has two explicit execution surfaces: **CLI Mode**, Wrightbench's focused GUI around Playwright CLI runs, and **UI Mode**, Playwright's embedded native UI. A separate global **History** destination consolidates retained results and evidence from both modes. This bundle documents the full journey — first launch through Settings — as 1440×900 desktop screens, each designed in **light (default) and dark**.

## About the Design Files
The files in this bundle are **design references created in HTML** — static artboards showing intended look and behavior, not production code to copy directly. Your task is to **recreate these designs in the target codebase's environment** (recommended: Electron + React or similar) using its established patterns. If no codebase exists yet, choose the stack (e.g. Electron + Vite + React + TypeScript) and implement the designs there. Do not ship the HTML as-is.

`Wrightbench.dc.html` contains every screen as a `<div data-screen-label="...">` artboard, all styles inline. Open it in a browser (keep `support.js` next to it) or read the markup directly — every color, spacing, and font value is literal in the file.

## Fidelity
**High-fidelity.** Colors, typography, spacing, radii, and copy are final. Recreate pixel-perfectly. Embedded Playwright surfaces (UI Mode, Trace Viewer, HTML report) are drawn as gray *wireframe placeholders* — in the real app these are `<webview>`/iframe panes hosting Playwright's own UI; do not rebuild their internals.

## Design Tokens
- **Type:** "Schibsted Grotesk" 400/500/600 for all UI; "Source Serif 4" 600 for display moments only (welcome headline 36px, Settings section titles 17px); "JetBrains Mono" 400/500 for code, paths, durations, commit hashes, run numbers. Base 13.5px / line-height 1.5; tables and trees 12–12.5px; status bars 11.5px; micro-labels (`PROJECTS`, `TESTS`) 10.5px/600, letter-spacing .09em.
- **Radii:** 14px window frame, 10–12px panels/cards, 8px controls, 7px list rows, 999px pills (search, watch toggle, chips, segmented controls).
- **Spacing:** titlebar 46px; tab strip ~42px (12px top / 9px bottom padding); toolbar rows 11px vertical padding, 10px gaps; status bar 30px; sidebar 262px; list rows 6px vertical padding.
- **Shadows:** near-none; cards use a 1px border + theme-scoped `--card-shadow` (`rgba(36,41,47,.06)` light / `rgba(0,0,0,.18)` dark).
- **Icons:** inline stroke SVG, 1.5px stroke, round caps/joins, 11–15px. No emoji, no gradients.
- Status dots: 7px filled circles (pass/fail/flaky); queued = 7px hollow circle (1.5px border `--t3`); running = 12px Playwright-green spinner arc (1s linear rotation).

## Interactions & Behavior
- For a test with recorded runs, the header strip switches Runs / Info / Video / Report / Trace; Runs is first and active by default, and selecting a run opens its Info view. The active tab keeps the 2px accent underline. Tests without runs show only Runs with the focused empty state; Info, Video, Report, and Trace appear after the first run starts. The contextual header actions remain **"Run and Capture"** (primary) and **"Debug in UI Mode"** (ghost) in both states. Sidebar project click switches active project (soft pill).
- Runs date range: after a test has at least one recorded run, its contextual action row shows a calendar control before Open file, Run and Capture, and Debug in UI Mode. The popover offers All time, Today, 7/30/90-day presets, and a keyboard-accessible custom start/end calendar. The selected range filters the outcome strip, pass/flaky/duration metrics, and recorded-run rows together; a zero-result range shows "No runs in this date range" with Show all runs. The range resets to All time when the selected test changes and is never shown for a never-run test.
- Test tree: chevron expands specs; clicking a test selects it.
- Debug in UI Mode lifecycle: the target-aware session starts only after the contextual action is invoked, never when the workspace opens. Back hides rather than unmounts a healthy embedded webview. Restart replaces the current session using the same resolved base target and project-owned environment. An observable idle embedded session is stopped before changing project/configuration; an opaque external or unsupported session must be stopped explicitly before those context changes. Stop UI Mode ends an embedded or external process and returns the takeover to its stopped state. Project removal, folder disappearance, app quit, server exit, and target invalidation also stop it.
- Execution ownership is exclusive. Starting **Run and Capture** first drains an idle, observable embedded session; if an embedded UI run is active, Wrightbench asks the user to stop it instead of racing output/artifact directories. External and unsupported embedded sessions are opaque, so their entire lifetime owns execution and Run and Capture stays disabled until **Stop UI Mode** or process exit. Conversely, while a Wrightbench run is active, **Run and Capture** becomes the fail-tinted **"Stop run"** action and Debug in UI Mode is disabled. A compatible embedded UI run streams to the same attempt-level history; an external/unsupported run makes no recording claim.
- Focused run lifecycle: Run and Capture on the selected test streams pass/fail/running state, attempts, steps, and logs into Info; the status bar shows progress and elapsed time; completion unlocks Info, Video, Report, and Trace for the recorded run. Stop run interrupts the tracked process group and preserves the interrupted outcome. The preserved suite runner still owns its original Run all → Stop run lifecycle when re-enabled.
- Watch toggle: pill turns to active (accent-tinted) state; watch runs get "Watch" trigger in history.
- Selected-test inspector: Runs owns analytics and exact prior-run selection; Info streams attempt, step and stdout/stderr events while a CLI run is active, shows persisted attempts after completion, and previews screenshots/diffs/other attachments; Video previews retained recordings in a centered, intrinsic-aspect player (1100px maximum width, container-responsive below that, viewport-height bounded, native controls, no forced autoplay); Report hosts that run's immutable HTML report; Trace hosts the exact retained trace in Playwright’s native viewer. All failure entry points converge on this Trace tab; there is no separate Wrightbench-built failure-analysis screen.
- Record: recording state uses the red dot; interactions happen in Playwright's headed browser and update Playwright's exact embedded Inspector. Record, locator picking, assertions, target language, copy, clear, pause/resume, and step use the native Inspector controls. Native **Stop Recording** pauses capture but intentionally keeps the session alive; the global **End session** action performs the clean Wrightbench shutdown and closes the browser.
- Hover states: list rows tint to `--panel`; selected rows use `--active-row` plus a green edge/icon; primary buttons move to `--ac-hover`; focus rings are 2px `--ac`.
- Theme switch applies instantly app-wide; System follows OS.

## State Management
- Workspace: projects[], activeProject, test tree with the latest recorded per-test status hydrated from SQLite. A body-only edit keeps that historical result; a rename, move, or line change that changes the persisted `file:line:title` identity returns to not-run until the declaration runs again.
- Runs: persistent run history (id, trigger, commit, per-test results, durations, artifacts paths) — local store (e.g. SQLite), retention-pruned.
- Derived analytics: pass rate windows, flaky % (pass↔fail alternation over last N runs), duration regressions (median deltas).
- Live run: streaming test events from Playwright reporter API → running/queued/passed/failed per test + progress counters.
- UI Mode session: selected project + requested target + resolved base configuration + project-owned environment + project-local Playwright version/CLI; launch mode (`embedded|external`), lifecycle (`stopped|starting|ready|running|stopping|failed|opaque`), recording support/progress, and retained webview URL/session identity. Renderer events are accepted only for the current target/session identity.
- Record session: project/target, lifecycle status, selected headed browser + viewport, current page URL, exact Inspector loopback URL, native Inspector protocol state, and latest generated source for stop recovery.
- Settings: nodeResolution (auto|fixed path), retention days, evidence policy/budget, theme, code font, density.

## Deviations from the artboards (intentional, product-driven)
The focused selected-test workspace and contextual hosted tools postdate the artboards. Where this README and `Wrightbench.dc.html` disagree on the points below, this README wins; everything else still follows the artboards exactly. Later numbered deviations supersede earlier ones when product navigation evolves.

**Current Record switch-recovery contract:** this supersedes the compact action wording in the project-switcher screen spec. When Record blocks project switching, the note reads **"Recording is active. End the session to switch projects."** A full-width, fail-tinted **End session** control sits directly beneath it, uses the canonical clean Record shutdown, becomes **Ending session…** in place, and leaves the menu open so the newly enabled project choices are immediately available.

1. **No global suite/tool tab strip.** The former Tests / UI Mode / Runs / Codegen navigation stays hidden. A selected test owns the workspace and exposes the evidence tabs Runs / Info / Video / Report / Trace only when applicable. The suite-level runner remains implemented but is not the current product surface.
2. **Two explicit execution paths.** The selected-test action row uses the exact labels **"Run and Capture"** and **"Debug in UI Mode"**. Run and Capture is Wrightbench-owned and creates retained attempts, evidence, history, and analytics. Debug in UI Mode is Playwright-owned and delegates filtering, projects, watch, debugging, snapshot updates, timeline, console, and network inspection to Playwright's native UI. Wrightbench does not reproduce those controls.
3. **Contextual full-width native UI.** Artboards 04–06 draw a split results list + UI Mode placeholder. Debug in UI Mode instead opens the full-width 04b takeover with Back; no sidebar or Wrightbench results panel competes with the native UI. Back hides but does not unmount a healthy embedded webview, so returning to the selected-test inspector preserves Playwright UI state. The integration bar is composed of existing primitives (Select, Button, StatusDot, Icon) and adds no tokens or kitchen-sink primitive.
4. **Target-aware launch and recovery.** Embedded UI Mode resolves the registered target in the main process and invokes its project-local Playwright CLI with canonical cwd, config, and project-owned environment. A run recipe maps to its base/full-suite configuration and is disclosed rather than silently forwarding recipe-only filters. Embedded startup or display failure offers one Retry UI Mode action using that same resolved target.
5. **Recording and exclusive ownership.** Compatible embedded UI Mode runs appear in history with trigger label "UI Mode" and count as manual in weekly analytics. Unsupported embedded and external sessions stay usable but are labeled opaque and make no recording/progress claim. Observable active UI runs and all opaque-session lifetimes block Run and Capture; Wrightbench runs disable Debug in UI Mode. Stop run and Stop UI Mode are always presented for the process Wrightbench currently owns.
6. **Sidebar PROJECTS list → project switcher dropdown.** Artboards 04–07 draw every project as an always-visible row; that list is now one compact dropdown (spec under 04/05 above) so the sidebar scales past three projects and gains in-place **"Import Playwright project…"** / **"Create a new Playwright project…"** commands (both reuse the existing screen-03 detection and create flows). Same tokens, spacing, and row anatomy as the original rows; the tree below is unchanged and the menu overlays it rather than pushing it down.
7. **Sidebar chrome, filters, and quick actions (no artboard).** The artboards draw a fixed 262px sidebar; it is now **resizable 220–380px** (drag handle on the right edge — 1px `--bd` divider with an 8px grab target, double-click resets 262, keyboard: `role=separator` with arrow keys ±10px, Home/End to min/max) and **collapsible** via a neutral sidebar-layout control in the global title bar's right action cluster, immediately before Search, or **⌘B / Ctrl+B** (never while typing in an input/webview). The control stays out of selected-test navigation because it changes window layout, not the active detail tab. Width, collapsed state, and per-project view context (expanded specs, selected test, query, status filter, scroll position — validated + bounded) persist in `settings.json → workspaceUi`; each project restores its own context on switch, pruned to tests/specs that still exist, and a removed project's context is deleted (its run history is not). The TESTS `filter` icon now opens an inline filter area: "Filter tests…" search (matches spec paths and test titles, case-insensitive, AND-combined with a single status select All/Failed/Flaky/Not run/Changed; **Changed = the spec file has uncommitted Git changes** via read-only `git status --porcelain -z`, refreshed with the debounced project invalidation — non-Git projects simply have no matches and say "Git status is unavailable for this project").
